## 0. สรุปผู้บริหาร

**คำตัดสิน: ระบบ "ใช้ได้บนกระดาษและในโลกจำลอง" ดีมากสำหรับงานของนักเรียน ม.ปลาย แต่ยังไม่ "พร้อมแข่ง" เพราะยังไม่เคยรันบนชิป ESP32 จริงแม้แต่ครั้งเดียว และยังไม่ครอบคลุมความเป็นไปได้ของโจทย์จริง 2 เรื่อง (ช่องทางสถานีภาคพื้น/กล้องคนละบอร์ด)** ความมั่นใจในคำตัดสิน: สูง (80%) ในส่วนที่ทดลองซ้ำได้บนคอม, ปานกลาง (55%) ในส่วนที่ต้องอนุมานไปยังฮาร์ดแวร์จริง

จุดแข็งที่ตรวจยืนยันแล้ว (ไม่ใช่คำชมลอย ๆ)
- ทดสอบซ้ำได้ครบและผ่านทั้งหมด: e2e 106/106 (core 3.x) และ 106/106 (core 2.x), Fallback 11/11, tool 55/55, ตรวจสูตร 45/45; `gen_cfg.js` สร้าง `cfg_table.h` และ `CONFIG_KEYS.md` ได้ไฟล์เดียวกับที่มี (ตรงกัน 100%)
- สถาปัตยกรรม "วัดแล้วหาจุด D = 0" (null-seeking) ของ V-sensor ทนมาก: ในโลกจำลองที่ผมสร้างใหม่ให้ **ไม่ตรงกับโมเดลของทีม** (กล่องกันแสงแบบวงกลมซ้อนกันจริง, γ ไม่คงที่, ADC ไม่เชิงเส้น, หลอดอยู่ใกล้ 12–25 ซม. ไม่ใช่จุดไกล) ตำแหน่งที่ M1 หยุดคลาดไม่เกิน ~0.15° เมื่อหลอดสว่างเปลี่ยน 0.2–4 เท่า (ยกเว้นกรณี ADC ไม่เชิงเส้นแรง ดู F05) แปลว่า **ความแม่นจริงของ M1 จะถูกจำกัดด้วยการตั้งศูนย์ (CAL TH0 กับของอ้างอิงที่วัดด้วยมือ) และกลไก ไม่ใช่สูตร**
- ตัวควบคุม M1 ลู่เข้าและแม่นแม้ LDR ช้า 6–20 เท่า, backlash 3.5° โดยไม่ชดเชย, มอเตอร์ข้าม step (575 step ที่ข้ามในการทดสอบ): ทุกกรณียังหยุดห่างเป้า < 1° (ดูหัวข้อ 5)
- โค้ด firmware อ่านแล้วไม่พบบั๊กระดับ "ทำให้ผลผิดเงียบ ๆ" ใหม่ (P1 ทั้ง 4 ข้อของรีวิวรอบก่อนแก้จริง และมีเทสต์ครอบ)

สิ่งที่ทำให้ยังไม่ปลอดภัย (ย่อ)
1. **F01 (P0)** ไม่เคย compile กับ ESP32 core จริง ไม่เคยรันบน ESP32 จริง — mock เขียนโดยผู้เขียนเดียวกัน ความผิดพลาดร่วมกัน (เช่น เข้าใจ API ผิด) จะไม่ถูกจับ ทั้ง NasaSat และ Fallback
2. **F02 (P0 แบบมีเงื่อนไข)** กำหนดการ 6 ต.ค. 13:00 เขียนว่า "การสื่อสารและควบคุมดาวเทียมผ่านสถานีภาคพื้นดิน" และ 14:30 "การเชื่อมต่อและสั่งงานกล้อง Payload" — ระบบปัจจุบันมีแต่ USB-Serial ตรงเข้าโน้ตบุ๊ก ไม่มี ESP-NOW/Wi-Fi ไม่มีโหมดกล้องคนละบอร์ด ไม่มีขากล้องบอร์ดยอดนิยมอื่น
3. **F03/F04 (P1)** ค้นหาแสงช้า 20–29 วินาทีเมื่อหลอดอยู่นอกมุมมอง และไม่ปรับตัวเมื่อ noise จริงสูง

ถ้าทำ 4 อย่างนี้ภายใน 4 ต.ค. โอกาสได้คะแนนสูงเพิ่มมาก: (ก) compile+ทดสอบบนฮาร์ดแวร์ ESP32-S3 ราคาถูกอย่างน้อย 1 ชุด, (ข) เตรียมทางออกสำหรับสถานีภาคพื้น/กล้องแยกบอร์ด, (ค) ปรับ SEARCH และความทน noise, (ง) เตรียมนำเสนอด้วยตัวเลขจริง ไม่ใช่ตัวเลขจำลอง

### สิ่งที่ตรวจแล้ว "ไม่มีปัญหา" (ไม่นับเป็นข้อพบ)
- โปรโตคอล, CRC32/CRC16, ตัวประกอบภาพ (ขอชิ้นซ้ำ 3 รอบ), ความยาวคีย์ NVS ≤ 15, `cfg_table.h` = registry ของ tool, ขนาด `LutBlob` ในขอบ NVS, `portMUX` ข้ามคอร์ OK, สแตก/แรม static เหมาะสม
- การชดเชย backlash ใน stepper: ทดลองกลับทิศหลายรอบ (probe `bl2.js`) offset คงที่ −0.61° (ทิศ +) และ −0.71° (ทิศ −) คือผลต่างเพียง 0.1° — ชดเชยทำงานจริง (ข้อสงสัยเรื่อง "ชดเชยหลอกตอนสั่งสองคำสั่งติดกัน" ผมตรวจแล้วไม่จริง ผลต่าง 0.1°)
- `sen.topo 1` ทำงานได้ (probe `topo.js`): ล็อกใน 4.0 s error ≤ 0.09° ทุกความสว่าง (ไม่มีใน e2e เดิม)
- `setRxBufferSize(4096)` หลัง/ก่อน `Serial.begin()`: เอกสาร Arduino-ESP32 (PR #8559) ยืนยันว่าเรียกเมื่อไหร่ก็จัดสรรบัฟเฟอร์ใหม่ได้ ข้อกังวลของผมก่อนค้นคว้า **ไม่จริง**
- เอกสารทฤษฎี: สูตร D = tanθ·tanα, conductance, ผลกระทบ flicker (sinc), อัตราทด 63.684, ลู่เข้า 0<k·r<2, pinhole camera ตรวจซ้ำถูกต้องทั้งหมด (`check_formulas.py` ผ่าน และผมคำนวณมือซ้ำ 6 ข้อสุ่ม)

## 2. รายละเอียดข้อพบ P0/P1

### F01 (P0) — ไม่เคยรันบน ESP32 จริง
หลักฐาน: README/TEST_PLAN/INSTALL_CHECKLIST ระบุเอง ("ยังไม่ได้ build ด้วย ESP32 SDK จริง") และ mock (`host_test/mock/*`, `sim.cpp`) เขียนโดยผู้เขียน firmware เดียวกัน
สิ่งที่ mock จับไม่ได้ (รายการตรวจหลัง flash ครั้งแรก เรียงตามความเสี่ยง)
1. **esp_timer คาบ 200 µs แบบ ESP_TIMER_TASK** (`stepper.cpp:28`) = ปลุก task 5,000 ครั้ง/วินาทีบนคอร์ 0 ตรวจ CPU load/ความสม่ำเสมอของพัลส์ (ใช้ scope หรือดูว่า `act.vmax 40` หมุนสม่ำเสมอไหม) — ถ้าไม่เนียน ให้เปลี่ยนเป็น `STEP_TICK_US 500` (vmax สูงสุด 2,000 step/s ยังเกินพอ)
2. **ADC จริง**: ช่วงอ่าน 0–3100 mV ที่ 12 dB (ยืนยันจากเอกสาร ESP-IDF S3) ค่าใกล้ 0 และใกล้เพดานไม่เชิงเส้น; mock ใช้เส้นตรง
3. **USB CDC**: ตั้ง "USB CDC On Boot" ผิด = เงียบ; ถ้าเป็น HWCDC การกดรีเซ็ต/REBOOT ทำให้พอร์ตหายและต้องเลือกใหม่ (F08)
4. **NVS**: `SAVE` เขียน 63 ค่า+LUT ตอน `Preferences.begin` ครั้งแรกบน flash ใหม่ (namespace ยังไม่มี) ควรเห็นบูต POWERON แล้ว SAVE/REBOOT/LOAD ได้ค่าเดิม
5. **กล้อง**: pin map, PSRAM OPI/QSPI, JPEG ได้ FFD9 ตรงท้ายจริงไหม (ตัวตรวจ `jpegOk` ยอมเศษท้าย 16 ไบต์), เวลา `esp_camera_init` จริง
6. **Loop WDT 5 s**: `M2 INIT`, `SAVE`, ส่งภาพ ต้องไม่ทำให้ loop ค้างเกิน 5 s
7. มาโคร `LINE_MAX` (F15), `enableLoopWDT()` มีใน core 2.0.17 และ 3.x จริง (ผมยืนยันจากเอกสาร)
การกระทำ (ลำดับ): (1) วันนี้: ติดตั้ง Arduino IDE+core **ทั้ง 3.3.x และ 2.0.17** บนเครื่องแข่ง แล้ว Verify ทั้ง NasaSat และ Fallback ทั้ง USB CDC On/Off; (2) ซื้อ/ยืม ESP32-S3 DevKitC + 28BYJ-48/ULN2003 + LDR 2 ตัว + ตัวต้านทาน 10 kΩ ส่งด่วน (ถึงก่อน 3 ต.ค.) ทำ TEST_PLAN B1–B5, B14, B15 อย่างน้อย; (3) ถ้าหาบอร์ดไม่ได้จริง ๆ ให้ถือ **NasaSat ไม่ผ่านการตรวจจนกว่าจะ compile ผ่านบนเครื่องแข่ง** และพกไฟล์ minimal-sketch (ดูข้อ 7.3)

(รวมแล้วไม่ใช่ 100% เพราะซ้อนกันได้)
ข้อเสนอที่ทำได้จริงก่อน 5 ต.ค. (ลำดับความคุ้ม)

3. เพิ่ม `cam.model 4 = AI-Thinker ESP32-CAM` (ขา: PWDN 32, XCLK 0, SIOD 26, SIOC 27, Y9..Y2 = 35,34,39,36,21,19,18,5, VSYNC 25, HREF 23, PCLK 22) และ DFRobot FireBeetle S3 / LilyGO T-Camera S3 (ตรวจ pin map จากแหล่งทางการก่อนใส่) และ **ตัวแยก `#define XXX_GPIO_NUM n` จากโค้ดผู้จัดที่ tool แล้วแปลงเป็นคำสั่ง SET** (ต้องทำให้ขากล้องเป็นค่า cfg แทน `board_config.h` — กันการ compile ใหม่หน้างาน)

### F03 (P1) — SEARCH ช้ามาก
ทดลอง (probe `search.js`, firmware C++ จริงใน host, ปรับเทียบแล้ว, ค่าเริ่มต้น):
| หลอด / จุดเริ่ม | เวลาถึง HOLD |
|---|---|
| 130° / 0° | 21.2 s |
| −120° / 0° | 27.0 s |
| 100° / −60° | 20.0 s |
| −150° / 20° | 28.7 s |
สาเหตุ (`procs.cpp:299`): เริ่มที่ m1.smin = −160° ไปสุดก่อนแล้วกวาดทีละ 20° แบบ หยุด–รอ 150 ms–วัด 60 ms ทุกจุด (17 จุด) แล้วค่อยกลับไปจุดที่สว่างสุด ถ้าโจทย์จริงให้หลอดอยู่หลังหรือข้างตัว (น่าจะมี เพราะ "ชุดทดลองให้หันเข้าหาแสง") เวลา 20–29 s อาจเป็นจุดที่เสียคะแนนความเร็ว
แก้: (1) เริ่มกวาดจากมุมปัจจุบันไปทีละ ±step สลับข้าง (ลดเฉลี่ย ~40%); (2) กวาดแบบต่อเนื่อง: สั่ง GOTO ไปสุดแต่ทุก window 20 ms บันทึก (มุม, S, sat) ที่ความเร็ว 40–55°/s ได้ S(θ) ทั้งช่วง 320° ใน ~6–8 s แล้ว slew ไปจุดสูงสุด (ประเมินรวม ~9–11 s จาก 20–29 s) (3) ตรวจช่วงมุมที่ตัวขับหมุนได้จริง (สายพัน) ก่อนเริ่ม ค่าใช้: 3–4 ชม. + ทดสอบใน host (เพิ่มเทสต์ lamp 130/−120)

### F04 (P1) — ไม่ทน noise จริง
ทดลอง (`robust.js`): ตั้ง `noiseMv 25` ในโลกจำลอง (สมเหตุสมผลถ้าสายไฟ/กราวด์/มอเตอร์รบกวน) ด้วยค่า M1 เริ่มต้น
- ล็อกใช้ 5.8–21.9 s (ปกติ 2–4 s), หนึ่งใน 4 กรณี error จริงหลังล็อก 1.51° (สูงสุด 2.13°)
- ลด deadband เป็น 0.15° (ตามที่ PLAYBOOK แนะนำเมื่อเกณฑ์ ≤ 0.5°): ไม่ล็อกใน 30 s ในสองกรณี
สาเหตุ: `ctl.meas` 60 ms (~50 คู่) และ `ctl.db` เป็นค่าคงที่ ไม่ขึ้นกับ noise จริง (0.1°/mV; 25 mV/√50 ≈ 3.5 mV ≈ 0.35° > db)
แก้ (ทำใน firmware): ระหว่าง MEAS เก็บ SD ของ mV ต่อ window → σ_θ; ใช้ `db_eff = max(ctl.db, 2σ_θ)` และถ้า σ_θ > db/3 ให้เพิ่มเวลาเฉลี่ยเป็นสองเท่าอัตโนมัติ (เพดาน 400 ms) + ส่ง `σθ` เข้า telemetry/DIAG; ฝั่ง tool เพิ่มปุ่ม "วัด noise" (RAW ×20 → σθ) ประมาณ 3–5 ชม. ยิ่งไปกว่านั้น: ช่วยตัดสินใจเรื่อง `act.hold`, สายชีลด์, ตัวเก็บประจุ 100 nF ที่ขา ADC (ถ้าผู้จัดอนุญาต)

### F05 (P1) — ตัวเลขจำลองไม่ใช่ตัวเลขจริง (ผลกับความแม่นและการนำเสนอ)
- โลกจำลองของทีมสร้างแสงด้วย cos^q × กฎยกกำลังของ LDR และตัวประมาณแก้ด้วยโมเดลรูปแบบเดียวกัน (e2e: fit rms 0.0005) จึงได้ 0.04–0.09° ซึ่งเป็น "การสอบข้อสอบที่ออกเอง"
- ผมสร้างโลกที่ไม่ตรงโมเดล (`probes/mismatch.js`, `mismatch2.js`): กล่องกันแสงเป็นรูวงกลมซ้อนกัน (ความลึก 1.5–4 มม.), γ เปลี่ยนตามความสว่าง (0.05/ln E), ADC ไม่เชิงเส้น (+40 mV ต่ำ, −60 mV สูง), หลอดที่ 12–25 ซม. ห่าง LDR 3 ซม. ผล:
  - ความคลาดภายในช่วงวัด หลังคาลิเบรต+LUT+TH0: MAE 0.06–0.10°, สูงสุด 0.27° (ที่ความสว่างเดิม)
  - ตำแหน่งที่ M1 ลู่เข้าเทียบความสว่าง 0.2–4×: ภายใน ±0.15° ในโลกที่ไม่มี ADC INL; กับ INL: +0.57° ที่ 4×
  - ในโลกกล่องลึก (3 มม.) ช่วงวัดแคบเหลือ ±25° และ **ค่า θ นอกช่วงอาจผิดมากโดยไม่ติดธง edge** (ตัวอย่าง: จริง 30° อ่านได้ 60° เพราะ |D| ยังไม่เกิน dmax ที่ fit ได้) ตัวควบคุมยังลู่เข้าได้เพราะหมุนเลยเป้าแล้วกลับ แต่เสียเวลาเพิ่ม
- ทดลองใน firmware จริง (host) เพิ่ม INL ของ ADC (`adcOff 40`, `adcComp 60`, topo 0): M1 หยุดห่างเป้า **−0.09° (K=1), +1.06° (K=0.3), −0.62° (K=2.5)** → ความสว่างต้องใกล้ตอนคาลิเบรต
- ความหมาย: ค่าคาดหวังจริงควรเป็น **0.5–1.5°** ไม่ใช่ 0.05–0.35°; เอกสารใช้คำว่า "แม่นกว่า 1° ในห้องทดลอง" และงบความคลาดรวม 0.35° (ผลรวมกำลังสองจากรายการในตาราง 5 จริง ๆ ได้ ~0.43° ถ้ารวมบรรทัดห้องเปิดไฟ) — ต้องกำกับว่าเป็นการคาดการณ์
- การกระทำ: (1) คาลิเบรตที่ระยะ/ความสว่างหลอดเดียวกับที่จะแข่ง (อย่าเลื่อนหลอด); (2) เก็บข้อมูลจริง B7/B8 ก่อนนำเสนอ; (3) ในสไลด์ใช้ตัวเลขจริงและบอกวิธีวัด; (4) แก้ตัวเลขในเอกสารให้ชัดว่าเป็นจำลอง (มีคำว่า "จำลอง" อยู่แล้วส่วนใหญ่ แต่ Q&A ข้อ 3, 4, 15 ควรทวนซ้ำ)

### F06 (P1) — Space ไม่ใช่ STOP

### F07 (P1) — ขั้นตอน "ไฟห้องเปลี่ยน ให้ทำ AMB+Sweep+Fit ใหม่" อาจทำให้แย่ลงและเสียเวลา
ทดลอง (`mismatch2.js`): หลังคาลิเบรตที่ ambient 0.03 เมื่อ ambient เปลี่ยนเป็น 0–0.3 โดย **ไม่** ทำอะไร จุดที่ M1 หยุดเลื่อนเพียง −0.14..+0.06° ส่วนการทำ AMB ใหม่ที่ ambient 0.15 (γ ที่ fit ได้ไม่ตรง γ จริง เพราะ γ กับ q แลกกันได้) ให้ −0.77°, −1.19°, −1.44°/−2.50° (หลอด 0.3×) ในโลกที่ไม่ตรงโมเดลสองแบบ และ −0.18°/−0.26° ในอีกสองแบบ เหตุผล: แสงห้องเพิ่มเท่ากันสองช่องไม่เลื่อนจุด D = 0 (ดูคณิตศาสตร์: eL = eR ยังเป็นจริง) แต่การลบด้วย γ ผิดทำให้เกิดความไม่สมมาตร
ข้อควรทำ: ตอนเช้าวันแข่ง (1) `RAW` ที่ตำแหน่งตรงหลอดตรวจ θ ≈ 0 และไม่ตัน (2) ตรวจจุดศูนย์ด้วยท่อเล็ง 1 จุด; ถ้าคลาด > เกณฑ์ → ทำ **CAL TH0 ใหม่อย่างเดียว** (30 วินาที) (3) ทำ AMB+Fit ใหม่เฉพาะเมื่อ S ตกจน valid หลุดหรือรูปแบบ D–มุมเปลี่ยนชัด
(ข้อยกเว้น: ห้องที่มีไฟกระพริบ/แสงเปลี่ยนเร็วระหว่างแข่ง — ทดสอบ)

## 3. การตรวจเชิงทฤษฎี

### 3.1 โมเดลของทีม (V-sensor, D=(L−R)/(L+R), conductance, γ, ambient, q, gain หลังถอดราก, LUT, CAL TH0)
**ถูกต้องและสมเหตุสมผล**: ลำดับการประมวลผลตรงกับฟิสิกส์ (G = Rf/R; E ∝ G^(1/γ); ลบแสงห้องในหน่วยแสง; ถอดราก q; คูณ gain หลังถอดราก) ข้อสังเกตที่ทีมควรรู้
1. **q กับ γ แลกกันได้** (log G = γ ln A + γ q ln cos) ถ้าไม่มีแสงห้องวัดได้ทั้งคู่ไม่ได้ การ fit จึงดึง γ เข้าหา datasheet ด้วย prior (0.05/หน่วย) — ทำให้ค่า γ ที่ได้ไม่ใช่ค่าฟิสิกส์จริง (ผมเห็น γ 0.75–0.95 ในโลกที่ γ จริง 0.57–0.62) และนี่คือต้นเหตุของ F07 อย่านำ γ จาก fit ไปอ้างกับกรรมการว่าเป็น γ จริงของ LDR
2. ระนาบ null (D = 0) ไม่ขึ้นกับความสว่างและแสงห้อง *ถ้า* gain ของสองช่องสมดุลที่ความสว่างนั้น — จึงควรนำเสนอ "null-seeking ที่ตั้ง gain balance" เป็นหลักการหลัก ส่วนโมเดล/LUT คือเพิ่มความเร็วการลู่เข้าและช่วงวัด
3. ความคลาดที่ใหญ่ที่สุดของจริงคือ **ตัวอ้างอิงศูนย์ (th0)** — ผมยืนยันเชิงตัวเลขว่า error 1° ในของอ้างอิงเท่ากับ error 1° ของตำแหน่งสุดท้าย (th0 ดูดซับทั้งหมด) ดังนั้น ออกแบบจิ๊กอ้างอิงให้ดี (ท่อเล็ง/เลเซอร์/เส้นที่ตีตามแกนกล้อง) สำคัญกว่าการปรับสูตร
4. หลอดไม่ใช่แหล่งจุด/ใกล้: ในโลกจำลองหลอด 12–25 ซม. ตำแหน่ง null ยังเลื่อน < 0.15° (เพราะสมมาตร) แต่ α ที่ fit ได้ลดเหลือ 22–26° (ไม่ใช่ 30°) — ไม่เป็นไรต่อ M1 แต่ตัวเลข α ที่รายงานไม่ใช่ค่าเรขาคณิตจริง
5. เรื่อง ADC: ปริมาณต่ำ (Rf 10 kΩ, LDR มืด) อยู่ใกล้ 0–100 mV ซึ่งไม่เชิงเส้นที่สุด และหลอดใกล้ทำให้ตัน (F18) — ข้อนี้แก้ที่การจัดแสง ไม่ใช่สูตร

### 3.2 วิธีที่ดีกว่า/ทนกว่า (จัดอันดับในหัวข้อ 6)
- **Null-seeking แบบสองจุดสมมาตร** (วัด D ที่ ±δ รอบเป้า หา zero-crossing เชิงเส้น): ตัด noise ที่ไม่สมมาตรและ INL เล็กน้อย; ประหยัด 1–2 iteration; จึงเหมาะเป็นขั้น "trim ท้าย" หลัง HOLD (เพิ่มแม่นขึ้น ~20–40% ของ σ)
- **Synchronous detection**: ใช้ได้ถ้าควบคุมหลอดได้ (ไม่ใช่) — ไม่คุ้ม
- **Dithering/stepper sweep หา peak**: S(θ) มีจุดสูงสุดกว้าง (cos) ไม่ดีกว่า D=0 ในระยะใกล้; ใช้ประโยชน์เฉพาะตอน SEARCH (ข้อ F03)
- **ลด flicker**: 20 ms window ถูกต้องสำหรับ 100 Hz; ถ้าหลอด LED ดิมด้วย PWM ความถี่อื่น (เช่น 200–1000 Hz) หน้าต่าง 20 ms ยังเฉลี่ยได้ดี; ปัญหาเฉพาะ PWM ความถี่ต่ำ (<100 Hz) — ดู `RAW` ซ้ำ ถ้า σ สูงผิดปกติให้ใช้ `sen.win 40`
- **Cross-correlation / model-free**: ไม่จำเป็น — โมเดล + closed loop ทำได้แล้ว

- สิ่งที่กรรมการน่าจะให้คะแนน (การอนุมาน): ภาพมีเป้าในกรอบ ชัด ไม่มืด/ไม่ไหม้ ส่งถึงเครื่องแสดงผล มีเวลา/มุม; ทีมควรมี **โหมดถ่ายรัว** `M2 BURST n` (n ภาพ, exposure ต่างกัน ±) เพื่อกันกรณีแสงไม่รู้ล่วงหน้า (ประมาณ 1–2 ชม.) และบันทึกภาพลงดิสก์อัตโนมัติในเครื่อง (ตอนนี้ต้องกด "บันทึกภาพ")
- boresight: เครื่องหมายอาจกลับด้านตามการติดตั้งกล้อง (F12) — หลังกด "ใช้ค่านี้" ต้องถ่ายซ้ำตรวจ ถ้าเป้าไกลกว่าเดิมให้สลับเครื่องหมาย

## 5. การควบคุม: ตัวเลขที่วัดจาก firmware จริง (host)

ปรับเทียบเหมือน wizard ของ tool (AMB → Sweep → Fit → push → CAL TH0) แล้วทดลอง M1 (เวลาในจำลอง)

**5.1 เวลาและ error สุดท้าย เทียบพารามิเตอร์ (τ LDR 25/35 ms, 5 จุดเริ่ม)**
| ชุดพารามิเตอร์ | HOLD (s) ต่ำสุด–สูงสุด | error จริงสุดท้าย |
|---|---|---|
| ค่าเริ่มต้น (k .85, wait 150, meas 60, vmax 40, nlock 3) | 1.75–4.40 | 0.09–0.27° |
| k 1.0 | 1.45–3.75 | ≤ 0.09° |
| k 1.0, wait 100, meas 40 | 1.15–3.30 | ≤ 0.09° |
| + nlock 2, vmax 70, acc 400 | 0.80–2.25 | ≤ 0.10° |
(ข้อควรระวัง: vmax 70°/s = ~794 step/s ซึ่งเกินความเร็วที่ 28BYJ-48 ขับด้วย 5 V ทำได้อย่างน่าเชื่อถือ (ประมาณ 400–600 step/s) โดยเฉพาะมีโหลด — ใช้ ≤ 50°/s และยืนยันด้วยจริง; LDR จริงอาจช้ากว่า 25 ms จึงต้องวัด τ)

**5.2 ความทนของตัวควบคุม (4 จุดเริ่มต่อสถานการณ์)**
| สถานการณ์ | ผล |
|---|---|
| LDR ช้า τ 0.15/0.40 s ด้วย wait 150 | ล็อก 3.3–9.6 s, error ≤ 0.27° |
| LDR ช้ามาก τ 0.5/1.2 s ด้วย wait 150 | ล็อก 8.9–12.7 s, error 0.09–0.89° (wait 1500: 15–18 s, ≤ 0.35°) |
| noise 25 mV | 5.8–21.9 s; error สุดท้ายสูงสุด 1.51°, สูงสุดหลังล็อก 2.13° (F04) |
| noise 25 mV + db 0.15 | ไม่ล็อกในสองกรณีภายใน 30 s |
| มอเตอร์ข้าม step (maxRate 450) | 575 step หาย แต่ล็อก 2.1–4.7 s, error 0.09–0.20° |
| backlash 3.5°, act.bl = 0 | ล็อก 2.1–5.3 s, error ≤ 0.10° (ปิด appr ได้ผลใกล้กัน) |
| `ctl.appr` 1 เทียบ 0 (14 จุดสุ่ม) | เวลาเฉลี่ย 2.52 vs 2.33 s; error 0.13 vs 0.14° — ต่างเล็กน้อย |
| appr 0 + k 1.0 + nlock 2 | 2.00 s เฉลี่ย, error 0.05° |
สรุป: ตัวควบคุมทนกลไกมาก จุดอ่อนจริง = **noise และการค้นหา** ไม่ใช่ backlash/ความหน่วง

**5.3 ข้อแนะนำจูนหน้างาน**: วัด σ (RAW ×20) และ τ (STREAM ON 100 + MOVE 3 แล้วดู θ(t)) ก่อน → ตั้ง `ctl.wait ≈ 5τ`, `ctl.meas` ให้ σθ ≤ db/3, `ctl.db` = 2σθ หรือเกณฑ์/2 (อย่างไหนมากกว่า), `ctl.k` 1.0 ถ้า r ≈ 1, `act.vmax` สูงสุดที่ไม่ข้าม step (ฟังเสียงมอเตอร์/ดู `missed`), `ctl.nlock` 2

## 8. การนำเสนอ/กรรมการ
- หลักฐานที่น่าประทับใจและหาได้จริง: (1) กราฟ θ(t) และ error(t) ของการลู่เข้าจากหลายมุมเริ่ม (จาก log ของ tool) (2) ฮิสโตแกรมความคลาดจาก 20 รอบ วัดด้วยท่อเล็ง/โปรแทรกเตอร์ (TEST_PLAN B8) รวมรอบที่พลาด (3) กราฟ D–มุม ก่อน/หลังคาลิเบรต ที่ความสว่าง 2–3 ระดับ (แสดงว่า null ไม่ขยับ = ข้อได้เปรียบของ conductance/null-seeking) (4) ภาพจากกล้องพร้อม metadata และจุดเป้าที่ตรงกลางภาพ (5) ตาราง FDIR (มีอยู่แล้ว)
- ข้อความที่ควรแก้ก่อนนำเสนอ: ตัดตัวเลข "0.35°"/"แม่นกว่า 1°" เว้นแต่มีข้อมูลจริง; อธิบายว่า γ ที่ fit เป็นพารามิเตอร์ของโมเดล ไม่ใช่ค่าฟิสิกส์ที่วัดได้ (F07/3.1); ข้อมูลประวัติดาวเทียมไทย (KNACKSAT 2018 / THEOS-2 2023) ผมไม่ได้ตรวจกับแหล่งปฐมภูมิ — ทีมควรเช็กอีกครั้งก่อนพูด
- เอกสารทฤษฎีถูกต้องเชิงสูตร (ดูหัวข้อ 1) เขียนชัด มีกล่อง "พูดกับกรรมการ" ใช้ได้; ข้อเสนอ: เพิ่มหนึ่งหน้า "สิ่งที่เรารู้ว่ายังไม่รู้" (ข้อจำกัดจำลอง vs จริง) — กรรมการมักชอบทีมที่ระบุข้อจำกัดเอง
- ทุกคนในทีมต้องอธิบายได้ว่า null-seeking ต่างจาก "อ่าน ADC ลบกัน" อย่างไร และอธิบายการ fit LM ได้แบบไม่เปิดเอกสาร
