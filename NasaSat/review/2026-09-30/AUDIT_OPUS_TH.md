- **ข่าวดี (VERIFIED)**: แก้แค่เปลี่ยนชื่อตัวแปร 1 ตัว (5 จุด) และย้าย `struct` 1 บรรทัด แล้วทั้งสองตัว compile ผ่านทุกโหมดที่ลอง (USB CDC ในตัว, UART/CH340, TinyUSB, PSRAM on/off และแม้แต่บอร์ด ESP32-CAM ตัวเก่า) ชุดทดสอบบนคอมยังผ่านครบหลังแก้ (106/106, 11/11)
- สถาปัตยกรรมโดยรวม**ดีกว่าระดับมัธยมมาก**: ตั้งค่าได้ทุกอย่างผ่าน `SET/SAVE`, protocol ชัด, loop ไม่ block, ไม่รายงานผ่านปลอม (ADC ตัน, snap_fail), ภาพมี CRC + ขอชิ้นซ้ำ, มีตัวจำลอง + เอกสารทฤษฎีที่สูตรถูกต้อง (ผมตรวจซ้ำแล้ว) — **จุดแข็งนี้ชนะได้จริง ถ้าไม่ตายที่ขั้น compile/ฮาร์ดแวร์**
- **ความเสี่ยงเชิงทฤษฎีที่ตัวจำลองมองไม่เห็น (VERIFIED ด้วย probe)**: ถ้ากล่องครอบ LDR สองข้างให้ "รูปทรงการตอบสนอง" ต่างกันแม้เล็กน้อย (q ต่างกัน 0.1) จุดศูนย์ของภารกิจ 1 จะ**เลื่อน ~2° ทุกครั้งที่ความสว่าง/ระยะหลอดเปลี่ยน 2 เท่า** (ต่าง 0.4 → ~7°) เพราะการ sweep ที่ความสว่างเดียวแยก γ ออกจาก q ไม่ได้ ตัวจำลองของทีมใช้ q เดียวกันทั้งสองข้างจึงไม่เคยเห็น ทางแก้ราคาถูกมีด้านล่าง
- **ช่องว่างใหญ่ที่สุดที่ยังไม่มีใครแตะ**: (1) ยังไม่เคยรันบนบอร์ดจริงเลย (2) ไม่มีโหมดทำงานแบบไม่ต่อสาย/ไร้สาย/สั่งเริ่มเองตอนเปิดเครื่อง ทั้งที่กำหนดการมีอบรม "สื่อสารและควบคุมผ่านสถานีภาคพื้น" (3) ภารกิจ 2 รองรับเฉพาะ "เป้าที่รู้มุม" ถ้าโจทย์ให้หาเป้าจากภาพ ต้องมีปุ่ม "คลิกภาพแล้วหัน" (4) ถ้ากล้องอยู่คนละบอร์ด (เช่น ESP32-CAM) ยังไม่มี preset

**สิ่งที่ต้องทำวันนี้ (30 ก.ย.)**: แก้ 2 บั๊ก compile, ใช้ `arduino-cli` บนเครื่องนี้เป็นด่านตรวจ compile ทุกครั้งที่แก้โค้ด, และหาบอร์ด ESP32-S3 + 28BYJ-48 + LDR มาทดสอบจริงก่อน 4 ต.ค.

### F04 (P1, กลไก VERIFIED / ขนาดจริง SUSPECTED) — จุดศูนย์เลื่อนตามความสว่าง เมื่อสองช่องมีรูปทรงต่างกัน
**ที่มา (ทฤษฎี)**: โมเดลของทีม `G_i = (K·A_i·cos^{q_i} + a_i)^{γ_i}` ตัวคำนวณมุมถอดราก `e_i = (G_i^{1/γ_i} − a_i)^{1/q_i}` (`estimator.cpp:14–17,33`)
- จาก sweep **ที่ความสว่างเดียว** ข้อมูลบอกได้แค่ผลคูณ γ·q ของแต่ละช่อง (log G = γ log K + γq log cos) แยก γ กับ q ไม่ออก ส่วน prior ของ γ ใน fit (`05_fit.js:156` น้ำหนัก 0.05) อ่อนมาก
- ถ้าแสงหลอดเปลี่ยนเป็น K เท่า: `e_i ∝ K^{1/q_i(จริง)}` → อัตราส่วน `e_L/e_R ∝ K^{1/q_L − 1/q_R}` **ไม่ตัดกัน** ถ้า q_L ≠ q_R (กล่องครอบสองข้างไม่เหมือนกัน, LDR ลึกไม่เท่ากัน, การตอบสนองเชิงมุมของ LDR แต่ละตัวต่างกัน)
- ตัวจำลองทั้งใน firmware (`host_test/sim.h:13` มี `q` ตัวเดียว) และในเว็บ (`07_sim.js` `truth.q`) ใช้ q ร่วม จึงไม่เคยเห็นปัญหานี้ และหัวข้อ THEORY 3.5 ที่อ้างว่า "หลอดเปลี่ยน 0.5–2 เท่าคลาดไม่ถึง 0.2°" เป็นจริงเฉพาะกรณี q เท่ากัน

**หลักฐาน (probe `scratchpad/audit_opus/probe_null*.js` ใช้โค้ด fit/estimator ของ tool จริง)**: คาลิเบรตที่ K = 1 (ตั้งศูนย์สมบูรณ์ที่ K = 1) แล้วดูว่ามุมจริงที่ตัวคำนวณอ่านได้ 0 อยู่ตรงไหนเมื่อหลอดเปลี่ยน

| q ซ้าย/ขวา (จริง) | แสงห้อง | K = 0.25 | 0.5 | 2 | 4 |
|---|---|---|---|---|---|
| 1.35/1.35 (เหมือนตัวจำลอง) | 3% | −0.33° | 0.04° | −0.32° | −0.83° |
| 1.30/1.40 | 3% | **3.98°** | 2.03° | −2.09° | −4.21° |
| 1.25/1.45 | 3% | **7.01°** | 3.68° | −3.90° | −7.88° |
| 1.20/1.60 | 30% | **≥10°** | 6.10° | −6.10° | ≥10° |

(K = 0.5 เทียบได้กับหลอดถอยห่าง √2 เท่า เช่น 50 → 71 cm)

**ทางแก้ที่พิสูจน์ในตัวจำลองแล้ว**: ถ้าได้ γ ของแต่ละ LDR ที่ถูก (หรืออย่างน้อยอัตราส่วน γ_L/γ_R ที่ถูก) **และ** ใช้รากร่วม q̄ = (q_L+q_R)/2 ทั้งสองช่องในตัวคำนวณ (ให้ LUT จัดการความต่างของรูปทรงแทน) จุดศูนย์ไม่ขยับเลย: ทุกกรณีในตาราง → **0.00° ทุกความสว่าง** และมุมนอกศูนย์ (±15°, ±30°) ที่ K = 0.5 คลาด ≤ 0.2–0.7°
- firmware **ไม่ต้องแก้** (ตั้ง `est.qL = est.qR = q̄` ได้ด้วย SET แล้วสร้าง LUT ใหม่จากค่านั้น)
- tool ต้องเพิ่ม "วัด γ ด้วย 2 ระดับแสง": หันหน้าเข้าหลอดนิ่ง ๆ, `RAW 1000` ที่หลอดปกติ, เปลี่ยนแสงหลอดโดยไม่เปลี่ยนทิศ (ถอยหลอด/เอากระดาษขาวบางคลุมหน้าหลอด), `RAW 1000` อีกครั้ง, + AMB → ในห้องมืด `γ_R/γ_L = ln(G_R1/G_R2)/ln(G_L1/G_L2)` (มีแสงห้องให้แก้ด้วยการแก้สมการ 1 ตัวแปรแบบวนซ้ำ) แล้วส่ง `fitPhysical(..., {fitGamma:false, gL, gR})` (ต้องเพิ่มให้รับ γ แยกตายตัว), ตั้ง qL=qR=q̄, สร้าง LUT
- เพิ่ม q ซ้าย≠ขวา (เช่น 1.25/1.45) ในความจริงของ `sim.h` และ `07_sim.js` เพื่อให้ e2e จับเรื่องนี้ได้

**ทางแก้เชิงขั้นตอน (ทำได้ทันที ไม่ต้องแก้โค้ด)**: คาลิเบรตและ `CAL TH0` **ที่ระยะ/หลอดเดียวกับตอนแข่ง** และทดสอบ "2 ระยะ": ล็อก M1 แล้วเลื่อนหลอดเข้า-ออกตามแนวเดิม ดูว่าหัวดาวเทียมขยับไหม (ถ้าขยับเกิน 0.5° แปลว่ามี F04 จริง ให้ทำทางแก้เชิงโค้ด หรืออย่างน้อยถามกรรมการว่าระยะหลอดคงที่ไหม)

### F08 (P1) — M1 มุมเป้า ≠ 0 ใช้ค่าประมาณนอกศูนย์
- `procs.cpp:332` `err = θ − tgt` → ต้องเชื่อค่าประมาณที่มุม tgt (ขึ้นกับ α, q, LUT, ความสว่าง) ในขณะที่จุดศูนย์ (θ = 0) คือจุดที่แม่นที่สุดของเซนเซอร์และ stepper หมุนมุมสัมพัทธ์ได้แม่นระดับ 0.1° (หลัง SPR + backlash)

- ชั่วคราวไม่แก้โค้ด: ถ้าโจทย์ให้ "ทำมุม X กับแสง" ใช้ `M1 START 0` ล็อก → `M1 STOP` → `MOVE −X` (ใช้ stepper ทำ offset) แล้วจดขั้นตอนนี้ใน PLAYBOOK

### F09 (P1) — HOLD ปล่อย error ค้างได้เกือบ 1°
- `procs.cpp:334–341`: ใน HOLD ถ้า `|err| ≤ ctl.hys (1.0°)` ไม่แก้เลย จุดล็อกเริ่มต้นอยู่ใน ±`ctl.db` (0.3°) แต่ถ้าหลอดถูกขยับ 0.8° หรือสาย USB ดึงตัวดาวเทียมภายในระยะ backlash (1–2° ของเฟือง ซึ่งไม่ต้องให้มอเตอร์หมุนก็ขยับได้) error จะค้าง 0.8° ตลอด

- เคล็ดลับกลไก: ดูว่าสายดึงตัวดาวเทียมไปทางไหน แล้วตั้ง `ctl.appr` ให้เข้าเป้าจากทิศที่แรงดึง "กดฟันเฟืองแนบ" อยู่แล้ว ตำแหน่งจะไม่หลุดในระยะ backlash

### F16 (P2) — sweep ทิศเดียว + LDR หน่วงหาง
- `procs.cpp:249–272` กวาดทางเดียว รอ 300 ms วัด 150 ms ตัวจำลองใช้ τ ลง 35 ms แต่ CdS จริงมีหางการคลายตัวหลายร้อย ms ถึงวินาที (โดยเฉพาะตอนแสงลดลง) ข้อมูลจะเอียงตามทิศกวาด
- **ทำ**: กวาดไป-กลับ (`SWEEP -60 60 5 400` แล้ว `SWEEP 60 -60 5 400`) เทียบ θ สองทิศ ถ้าต่าง > 0.2° เพิ่ม dwell หรือเฉลี่ยสองทิศก่อน Fit (tool รวมได้ง่าย)

### F17 (P2) — ตั้งขาที่ทำให้ USB ตายได้
- `cfg_table.h` ให้ `sen.pin*`, `act.in*`, `act.spin` เป็น 0..48 ถ้าเผลอตั้ง 19/20 (USB D−/D+ ของ S3) `pinMode(OUTPUT)` หรือ `analogRead` จะตัด USB ทันที (บนบอร์ด USB ในตัว) และถ้า SAVE ไว้ บูตครั้งหน้าก็หลุดอีก ต้องล้าง flash
- **แก้**: ใน `commands.cpp` SET ของคีย์ขา ปฏิเสธ 19, 20 (และ 26–32 flash, 33–37 ถ้ามี OPI PSRAM) ด้วย `ERR PIN`

### F18 (P2) — ตัวเลขนำเสนอที่สวยเกินจริง
- "M2 เทียบดวงอาทิตย์คลาด 0.002°", "MAE 0.04°", "หลอดเปลี่ยน 0.5–2 เท่าคลาด < 0.2°" มาจากโลกจำลองที่มี CAL TH0 ด้วยค่าความจริง (e2e ส่ง `CAL TH0 ${truth}` ตรง ๆ) ของจริงถูกจำกัดโดยของอ้างอิง (โปรแทรกเตอร์ด้วยตา ±0.5–1°) และ F04
- **ทำ**: สไลด์ใช้ตัวเลขจากการวัดจริง (TEST_PLAN B7/B8) เป็นหลัก ตัวเลขจำลองวางเป็น "ขีดจำกัดทางทฤษฎี" พร้อมบอกข้อจำกัดของตัวจำลอง (F04, หางของ LDR) กรรมการสายวิศวะจะให้คะแนนความซื่อตรงนี้มากกว่าตัวเลข 0.002°

## 4. สิ่งที่ตรวจแล้ว "ดีอยู่แล้ว" (ไม่ต้องแตะ)

- **API core 3.x/2.x**: `ledcAttachChannel` 14 บิต @50 Hz (ช่อง 6, ไม่ชนกล้องช่อง 0), `esp_timer` 200 µs แบบ TASK + spinlock, `Preferences` (ชื่อคีย์ยาวสุด 11 ตัวอักษร ≤ 15, blob LUT ≤ 1 KB), `Serial.setRxBufferSize` ก่อน `begin`, `analogReadMilliVolts` — ทั้งหมด compile กับ SDK จริงผ่าน ไม่มี warning
- **สูตรในเอกสาร**: D = tanθ·tanα, G = V/(Vcc−V), ความไววงจรแบ่งแรงดัน Vcc·γ/4, sinc ของไฟกระพริบ, เฟือง 63.684:1 = 4075.8 step, เงื่อนไขลู่เข้า 0 < k·r < 2, pinhole f = 533 px — ผมตรวจซ้ำ (`check_formulas.py` 45/45 และคำนวณเอง) ถูกทั้งหมด ข้อมูล KNACKSAT (3 ธ.ค. 2561) และ THEOS-2 (9 ต.ค. 2566, Vega VV23) ถูก
- **ตรรกะควบคุม**: วัดเฉพาะตอนหยุด, รอ LDR ก่อนวัด, k = 0.85 < 1, เข้าเป้าจากทิศเดียว + ชดเชย backlash ในตัว stepper (`comp_` ไม่เปลี่ยนตำแหน่งตรรกะ), ขีดจำกัดมุม, SEARCH ข้ามจุดที่ตัน — ออกแบบถูกหลักสำหรับเซนเซอร์ช้า + ตัวขับตำแหน่ง
- **ไม่รายงานผ่านปลอม**: ADC ตัน, snap_fail, ERR RANGE, ตัวตัดสิน M1 แบบทุก sample, ภาพ CRC32 + ARQ — ตรงกับที่รีวิว 24 ก.ย. ขอ และทดสอบซ้ำแล้วผ่าน
- **เวลาเข้าเป้า** (จำลอง): 4.4 s จาก 75°, STEP 10° กลับใน 2 s — เร็วพอสำหรับการแข่ง ไม่ควรเร่งเพิ่มโดยเสียความนิ่ง
