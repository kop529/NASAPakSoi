## เตรียมล่วงหน้าได้แน่นอน — และควรทำด้วย

ตอบสั้นๆ ก่อน: **ทำได้ และไอเดีย calibration tool ของคุณคือวิธีที่วิศวกรดาวเทียมจริงใช้กัน** เรียกว่า sun sensor characterization ครับ

### สิ่งที่เขียนโค้ดรอไว้ได้เลย (ไม่ต้องรู้ฮาร์ดแวร์)

| ระบบ | เตรียมล่วงหน้าได้ | ต้องรอของจริง |
|---|---|---|
| **OBC** | State machine, task scheduler, command parser, telemetry logger, watchdog | เกือบไม่มี — ทำได้ 90% |
| **ADCS** | PID controller, sensor fusion, algorithm แปลงค่าแสง→มุม, slew logic | ค่า gain ที่จูนกับมอเตอร์จริง |
| **สื่อสาร** | Packet format, CRC, ACK/retry, chunking, ground station UI | เลือกโมดูล (LoRa/NRF24/WiFi) |
| **EPS** | โค้ดอ่าน INA219/226, battery model, low-power mode | วงจรจริง |
| **Payload** | Trigger logic, ตั้งชื่อไฟล์, บีบอัด, ส่งภาพเป็น chunk | รุ่นกล้อง |

**กุญแจสำคัญ: เขียนแบบ HAL (Hardware Abstraction Layer)** — แยกชั้น "ตรรกะ" ออกจาก "ไดรเวอร์เซนเซอร์" พอถึงหน้างานรู้ว่าใช้เซนเซอร์อะไร คุณแค่เขียนไฟล์ driver ใหม่ไฟล์เดียว ตรรกะทั้งหมดไม่ต้องแตะ

class SunSensor:          # interface
    def read_raw(self): ...
class LDRArray(SunSensor):  # เปลี่ยนแค่ตรงนี้ตอนรู้ของจริง
    def read_raw(self): ...

### Calibration Tool ที่คุณคิด — ทำได้ และนี่คือวิธี

**หลักการ:** เซนเซอร์แสงแต่ละตัวไม่เท่ากันเลย (LDR ต่างกันได้ 20-30%) จึงต้องหาความสัมพันธ์ "ค่าดิบ → มุมจริง" ด้วยการวัดเอง

**ขั้นตอน**
1. ทำจิ๊กหมุนที่มีสเกลองศา (แผ่นโปรแทรกเตอร์ + แกนหมุน หรือใช้ stepper motor เป็นตัวอ้างอิงมุมเลยยิ่งดี)
2. ตั้งไฟส่องนิ่ง หมุนทีละ 5° ครอบคลุม −90° ถึง +90°
3. แต่ละจุดกดบันทึก → tool เก็บค่าดิบทุกช่อง + มุมจริง
4. Export CSV → เอาไป fit สมการ

**Schema ที่ควรเก็บ**
csv
timestamp,true_angle_deg,s0,s1,s2,s3,ambient_dark,temp_c,light_dist_cm
- ambient_dark = ค่าตอนปิดไฟ ไว้ลบ offset (สำคัญมาก เพราะแสงห้องแข่งจะไม่เหมือนที่คุณซ้อม)
- เก็บ 3-5 ครั้งต่อมุม แล้วเฉลี่ย ลด noise

**สูตรที่ใช้จริง** — เซนเซอร์แสงมีพฤติกรรมตาม cosine law ($I = I_0\cos\theta$) ถ้าวาง 2 ตัวเอียงเข้าหากัน ใช้ค่าเชิงอัตราส่วนจะกันเรื่องความสว่างเปลี่ยนได้:

$$\theta \approx \arctan\left(\frac{s_A - s_B}{s_A + s_B}\right) \cdot k$$

หารด้วยผลรวมทำให้ **ไม่ขึ้นกับความแรงของแสง** — เอาชนะปัญหาไฟห้องแข่งสว่างไม่เท่าที่ซ้อม ซึ่งเป็นจุดที่ทีมส่วนใหญ่พลาด

### ส่วน "ส่งให้ AI" — ขอเตือนตรงๆ

**Machine Learning ไม่ใช่คำตอบที่ดีที่สุดตรงนี้ครับ** ให้ AI ช่วย วิเคราะห์และหาสมการ ดีกว่าให้ AI เป็นตัวประมวลผลบนบอร์ด

| วิธี | ข้อดี | ข้อเสีย |
|---|---|---|
| Lookup Table + interpolation | เร็วมาก, debug ง่าย, ไม่มี surprise | กินหน่วยความจำนิดหน่อย |
| Polynomial fit (deg 3-5) | โค้ดสั้น, แม่นพอ | ระวัง overfit ปลายช่วง |
| Neural net เล็ก | รับ non-linearity ได้ดี | overfit ง่ายมากกับข้อมูล ~100 จุด, กรรมการอาจถามแล้วอธิบายไม่ได้ |

**แนะนำ:** ใช้ AI ช่วยหา best-fit จาก CSV ของคุณ → ได้สัมประสิทธิ์ออกมา → ฝังเป็นสมการคงที่ในโค้ด ได้ทั้งความแม่นและอธิบายกรรมการได้ ซึ่งมีคะแนนแน่นอน

## ออกแบบให้ "วนลูปแก้ไขหน้างาน" ได้เร็วที่สุด

### 1. อย่าให้ต้อง flash ใหม่ทุกครั้ง
นี่คือตัวฆ่าเวลาอันดับหนึ่ง ให้ค่าคาลิเบรตทั้งหมดอยู่ใน**ไฟล์ config ที่อ่านตอน runtime** (JSON บน SD card หรือ EEPROM) แล้วมีคำสั่ง serial SET k_p 0.45 + SAVE + RELOAD — แก้ค่าได้ใน 3 วินาที แทนที่จะ compile+upload 2 นาที

> SET adcs.kp 0.45
> SET sensor.offset[2] -18
> SAVE
> RUN mission1

### 3. เตรียม "Context Pack" ไว้ล่วงหน้า
ไฟล์ Markdown ไฟล์เดียวที่แปะให้ AI ตอนเริ่มงาน มี pin map, รุ่นเซนเซอร์, โครงสร้างไฟล์, สมการที่ใช้, ข้อจำกัดภารกิจ — จะได้ไม่ต้องเสียเวลาอธิบายใหม่ทุกรอบ แล้วคำตอบจะตรงจุดกว่ามาก

### 4. Built-in diagnostic commands ที่ควรมี

| คำสั่ง | ทำอะไร |
|---|---|
| SWEEP | หมุนช้าๆ ทั้งช่วง พิมพ์ตาราง มุม vs ค่าเซนเซอร์ |
| STEP 30 | สั่งหมุน 30° แล้วรายงาน rise time / overshoot / settle |
| DARK | เก็บค่า ambient แล้วเซ็ต offset อัตโนมัติ |
| SELFTEST | เช็คทุกระบบย่อย ตอบ PASS/FAIL รายข้อ |

ทั้ง 4 อันนี้ทำให้ "รอบการทดลอง 1 ครั้ง" เหลือไม่กี่สิบวินาที — ซึ่งคือสิ่งที่ตัดสินแพ้ชนะจริงๆ ในสนามที่มีเวลาจำกัด

## ⚠️ สองเรื่องที่ต้องเช็คก่อน มิฉะนั้นแผนนี้พังทั้งแผน

**1. กติกาอนุญาตให้ใช้ AI ระหว่างแข่งไหม** — เอกสารโครงการไม่ได้ระบุเรื่องนี้เลย บางรายการห้ามใช้เน็ต บางรายการห้ามเปิดอุปกรณ์นอกเหนือที่จัดให้ ต้องถามผู้จัดให้ชัดครับ

**2. มีอินเทอร์เน็ตหน้างานไหม** — ถ้า WiFi ล่มหรือไม่ให้ใช้ ต้องมีแผนสำรอง แนะนำเตรียม **ซิมมือถือ + tethering** และที่สำคัญกว่านั้นคือ **checklist การจูนแบบ manual** ที่คุณทำเองได้โดยไม่พึ่ง AI เลย

> หลักคิดที่ปลอดภัย: **ให้ AI เป็นตัวเร่งความเร็ว ไม่ใช่ตัวที่ขาดไม่ได้** ถ้าไม่มีก็ยังจบงานได้ แค่ช้าลง

## สิ่งที่ควรทำก่อนถึงวันแข่ง

**ซ้อมลูปนี้จริงที่บ้าน** อย่างน้อย 2-3 รอบ — ต่อบอร์ด, รัน `SWEEP`, แปะ output, รับคำแนะนำ, แก้ config, ทดสอบซ้ำ จับเวลาดูว่าใช้กี่นาที ถ้าเกิน 10 นาทีต่อรอบ แปลว่าเครื่องมือยังไม่ดีพอ ต้องกลับมาปรับ

โครงการลงทุนทำบอร์ดเฉพาะไปแล้ว มักใช้ต่อเพื่อความคุ้ม

เหตุผลที่อาจเปลี่ยน/เพิ่ม

รอบชิงมีภารกิจ Target Imaging ที่รอบภูมิภาคไม่มี → ต้องมีกล้องเพิ่มแน่นอน (OV2640/OV5640 หรือบอร์ดกล้องแยก)

LDR 2 ตัวให้ได้แค่แกนเดียว ถ้ารอบชิงต้องการ 2 แกนก็ต้องเพิ่มเป็น 4 ตัว
